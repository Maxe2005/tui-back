## Intent

**Problem:** A consumer's update merge conflicts on the `shared-types` version line of `package.json` (and on `package-lock.json`), forcing the developer to hand-manage `shared-types` versions.

**Approach:** On every mid-run merge/pull conflict, always try to settle the `shared-types` version for the developer, even when other files or other `package.json` hunks also conflict. The version kept is the one published earlier in this same run (4.4 phase, already part of the EDT); with no publication in the run, the consumer's own (EDT) value. Resolved: the `shared-types` line in `package.json`, then `package-lock.json` taken from the EDT side and regenerated by `npm i` and staged. The merge is then retried to completion; whatever remains conflicting is left to the developer through the existing assisted flow. If the line itself cannot be resolved, that is reported as an issue in the incident queue.

## Boundaries & Constraints

**Always:** Core stays generic: `group-update` gains only an optional `autoResolveConflict` seam and never names `shared-types`; the resolver lives in `core/shared-types/` and receives the ports. Only conflict blocks whose two sides differ solely by the `shared-types` line are rewritten; every other block, file and marker is left byte-for-byte. `npm i` runs only once `package.json` holds no conflict marker. The seam runs before each menu presentation and again after the developer's `edited` choice (idempotent), so when `package.json` could not be fully settled automatically, `npm i` runs by itself as soon as the developer has resolved it, and the regenerated `package-lock.json` is staged before the merge is finalized. Every git write passes the safety gate (AD-8); applies to merge and pull conflicts; nothing is pushed. A conflict block mixing the `shared-types` line with other differing lines is not rewritten and is reported as an issue.

**Ask First:** If the version published in the run cannot be obtained from the 4.4 phase result without changing 4.4's behaviour, HALT and ask.

**Never:** No CLI/script change (the seam is wired by the TUI store only). No new config row. No new blocker kind or choice (the issue is a note on the existing `merge-conflict` incident). No auto-resolution of any other hunk or file. No change to 4.2/4.3/4.4 behaviour.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| st line only | `package.json` (+ lock) unmerged | Line set, lock from EDT side, `npm i`, lock staged, merge finalized; row `auto-resolved` | N/A |
| Published in run | 4.4 phase published version V | V kept on the line, else the consumer's own value | N/A |
| Other files conflict | st line resolved, other path unmerged | st + lock settled, rest left to developer; row `partial` | N/A |
| Other `package.json` hunks | st block resolved, other blocks remain | Markers of other blocks kept, `npm i` deferred; lock regenerated after the developer finishes | N/A |
| Unresolvable line | st block mixed with other lines, or line missing | Nothing rewritten; issue note on the conflict incident; row `left-to-user` | `npm i` failure also becomes an issue note |
