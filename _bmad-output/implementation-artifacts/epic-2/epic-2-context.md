# Epic 2 Context: EDT Workspace Management

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

A developer can create, modify, and safely switch between EDTs (isolated per-topic workspaces spanning a manually chosen set of member services) without ever losing uncommitted work, with branch and upstream-divergence visibility across every managed repo — member or not — and a hard guarantee that a shared/protected branch (`development`, preprod, prod) can never become an EDT's "own" branch, and that non-member repos stay parked on `development`. This is the foundation every later epic (group update, shared-types propagation, logs, routes) scopes its actions against. The epic branch stayed open past its original nine stories to absorb five appended, review-cycle-discovered fixes/refinements (stories 2.10–2.14) whose affected code sometimes sits under Epic 1's territory but whose branch was still open, per the project's one-branch-per-epic convention.

## Requirements & Constraints

- A developer creates an EDT with a unique topic and at least one manually selected member service; duplicate topics and zero-member creation are both rejected before anything is written.
- Optionally, working branches are created per member at EDT-creation time, based on a chosen base branch (default `development`), named either identically across all selected services (grouped) or individually per service; a single service's branch-creation failure (missing base, name collision) is reported without aborting the rest of the batch.
- After creation, member services can be added/removed (including down to zero, which is a valid, non-error state) and a member's branch can be changed or the topic renamed, each independently, without disturbing other members' recorded state.
- Assigning a shared/protected branch (`development`, preprod, prod) as any EDT's own branch for a service is always rejected, with a clear explanation, before any git write — at creation, at branch change, and at any other write path.
- Switching the active EDT never loses uncommitted work: it is auto-preserved in every affected repo of the outgoing EDT before the switch. After a switch, every member sits on its EDT-registered branch and every non-member managed repo sits on `development` (or its manifest-configured shared branch), regardless of that repo's membership in some other, inactive EDT. A non-member repo missing `development` locally is fetched first. A service can belong to multiple EDTs at once, each tracking its own branch for it independently.
- Every managed service (member or not) shows its current branch and ahead/behind divergence from upstream; no upstream shows an explicit "no upstream" state, and being offline shows an explicit "unknown (offline)" state — never a stale or zero value standing in for missing data.
- The tool's repo registry can be populated from the TUI (not just the CLI): a developer scans a root path for manifest-carrying directories, multi-selects candidates, and registers them, with per-path outcome reporting and a distinct "nothing found" state; the tool always shows static guidance for creating a manifest by hand or via a manifest-generator skill. That guidance describes `migrationCommand` as optional (a manifest may omit it — the service is then treated as having no migrations), matching the manifest schema's actual (relaxed) contract, not a required field.
- Zone tabs for manifest-gated modules (Routes, shared-types) must never claim availability that doesn't exist and never hide a capability that does exist somewhere: fully omitted only when no repo anywhere in the registry could ever activate the module; shown disabled-with-explanation when the module exists in the registry but not on the active EDT's membership.
- `Left`/`Right`, with nothing capturing input, directly switch the active zone to the previous/next zone in tab-bar order, wrapping at the ends (skipping fully-omitted tabs, landing on disabled ones) — always available, no intermediate focus mode to enter first. `Tab` is completely unaffected by this.
- `:` opens a real command-entry bar (a `modal-dialog` with a text input and a filtered `list-row` candidate list of registered commands): typing filters by name-prefix; `Tab` autocompletes an unambiguous match; `Enter` runs an exact match and closes the bar, or shows an inline "unknown command" message on no match; `Esc` cancels. It never stacks on another overlay, and it fully consumes `Tab` while open (no conflict with `Left`/`Right` zone switching). The repo registry screen (Story 2.11) is reachable only as this bar's first registered command (`registry`) — `:` itself never opens it directly.
- A second TUI launch attempt must be recoverable rather than a dead end: a stale (dead-pid) lock is reclaimed automatically and silently; a live lock prompts (TTY only) to kill-and-take-over, defaulting to refuse on decline/no-input/non-TTY, exactly as before.
- Blast-radius isolation: a crash or bug touching one EDT's data must never affect another EDT's data.

## Technical Decisions

- **Storage:** one SQLite file per EDT at `XDG_DATA_HOME/tui-back/edts/<ulid>.db` — filename is a generated ULID, never the topic (topic lives as a field inside the file; uniqueness is checked across existing files). This is also why renaming a topic needs no file rename/migration. Active-EDT pointer and other transient UI state (last-used EDT, per-zone splitter sizes) live in `XDG_STATE_HOME/tui-back/state.json`, never inside a `.db`. Each `.db` evolves via hand-rolled numbered `.sql` files tracked by a `schema_version` table.
- **Git safety gate:** every git write goes through `adapters/driven/git`, which resolves the allowed-branch context itself (current EDT/manifest state via `EdtStorePort`/`ManifestPort`) and rejects — before invoking `git` at all — any write targeting a shared branch or a branch that isn't the current EDT's own registered branch for that service. It never trusts a caller-supplied branch name. A branch switch always auto-preserves uncommitted work first and re-verifies the resulting state rather than assuming success.
- **Locking:** two independent mechanisms — the interactive TUI refuses to start a second instance via an exclusive-create lock file at `XDG_STATE_HOME/tui-back/locks/tui.lock` (TUI-only, never blocks a hand-run CLI subcommand); separately, any state-mutating use-case acquires a short-lived advisory lock scoped to the specific EDT id / repo path(s) it touches before writing, releasing it after. Story 2.10 corrects the v1 gap: a dead-pid lock is now auto-reclaimed (no prompt) instead of treated as held; a live-pid lock triggers a TTY-only `y/N` prompt naming pid + start time, offering signal-terminate → brief wait → force-terminate → lock-acquire, with permission failures reported and never falling through to deleting the lock out from under an unstoppable process. Non-TTY invocations and any CLI subcommand keep today's unprompted refuse-immediately behavior unchanged.
- **Cross-zone state:** lives in exactly one Zustand store; zone-local UI state (list cursor, scroll position) stays component-local. The store's `activeEdt` field is a hydrated cache of `state.json` (the durable, authoritative record), re-synced via `fs.watch`/poll so a CLI-made change is picked up live while the TUI is open. Story 2.12's zone-switching is a pure wrap function over tab-bar order plus one dispatch branch in `AppShell` — no new store state, no focus-mode state machine (an earlier focus-based design was rejected in review for leaving focus stuck on the tab bar across overlay open/close).
- **Command registry (Story 2.14):** a small in-memory, statically-defined list (command name → handler) inside `adapters/driving/tui`, no core/port change — mirrors Story 2.11's own "no new port/adapter" rule. Only one command (`registry`) is registered initially; adding a second is registry-only, no shell-level change needed.
- **CLI/TUI parity (relevant to Story 2.9):** the TUI must call `core/edt/create.ts` / `switch.ts` / `modify.ts` in-process — the same core use-cases the CLI subcommands wrap — never by shelling out to the CLI. Story 2.11 likewise reuses Story 1.5's existing `scan`/`register` use-cases as-is; no new port/adapter.
- **Manifest-gated tab visibility (Story 2.13):** requires loading manifests for *all* registered repos (not just active-EDT members) at shell level to decide full-omission vs. disabled state — flagged as needing verification against the cold-load spinner state. A tab can newly appear/disappear when the registry changes (Story 2.11) or become enabled/disabled when EDT membership changes; if the active zone's tab disappears entirely, the app falls back to Dashboard, with no forced navigation on a mere disable (the zone's content switches to the explanatory message in place instead).
- **Manifest schema note:** `migrationCommand` is an optional field on the manifest (absent = service has no migrations); this relaxation (originally required) is documented here because it directly affects Story 2.11's onboarding-guidance text, though the schema/port change itself lives in Epic 1's already-shipped manifest loader.
- **Conventions carried through this epic:** generated EDT ids are ULIDs; dates/times ISO 8601; any per-service outcome (e.g. batch branch creation, per-path registration) reports via a `data.results: {service, outcome, detail?}[]` shape with `outcome` from a shared closed set; error codes are kebab-case strings.
- **`edts/` zone maps 1:1 to `core/edt`** per the TUI's zone-to-capability-boundary convention; shared visual primitives (list/detail split, modal-dialog, footer-hint, checkbox-list-item, command-bar) live in `tui/shared/`, never duplicated per zone.

## UX & Interaction Patterns

- **Canonical keybinding contract for list navigation is arrows + Home/End** (superseding the originally planned vim-style `j`/`k`/`g`/`G`, retired as impractical). `Home`/`End` jump to top/bottom of the focused list and never switch zones. `Tab` keeps its pre-existing role — cycling list/detail panes or splitter boundaries inside a form/resize-mode — and is never repurposed as a list-movement key. After Story 2.7, `j`/`k`/`g`/`G` trigger nothing anywhere in the app.
- **Fullscreen rendering (Story 2.8):** on launch in a TTY the app takes over the terminal via the alternate-screen buffer, sized to current rows/columns; a terminal resize re-renders without artifacts; on quit/Ctrl+C/crash the original screen content is restored with no leftover TUI output. This underlies every zone's chrome, EDTs zone included.
- **EDTs zone states:** empty (explicit "create the first EDT" prompt, never a bare empty list); populated (service list with branch + ahead/behind divergence, uniformly shown whether the service is a member or not); duplicate-topic and zero-member-at-creation rejections; per-service branch-creation failure reported without blocking the batch; shared-branch rejection explained before any git write; member add/remove without disturbing other members; zero-member EDT shown as valid, not an error; protected-switch rule on member branch change; switch-blocked-during-update prompt with an offer to stop the run; interrupted-update recovery offer on return. Composition question (flagged, not resolved by planning): whether the EDT selector groups/filters the flat service list or replaces it with a grouped-by-EDT view is left to implementation time.
- EDT member selection at creation, and any later multi-select action, uses the `checkbox-list-item` pattern (`Space` toggles, `Enter` confirms the whole selection). The same pattern drives Story 2.11's scan-candidate multi-select.
- **Zone arrow navigation (Story 2.12):** `Left`/`Right`, with no form/overlay capturing input, directly switch the active zone to the previous/next reachable zone in tab-bar order, wrapping at the ends (skipping fully-omitted tabs, landing on disabled ones per Story 2.13). No focus-mode state to enter/exit. Zone mnemonics (`d`/`e`/`u`/`l`/`r`/`s`) are unaffected and keep working immediately from anywhere.
- **Manifest-gated tabs (Story 2.13):** Routes/shared-types are fully omitted (mnemonic and arrow-navigation never land on them) only when zero registered repos anywhere activate the relevant module; otherwise, if the active EDT has no qualifying member, the tab shows dimmed/strikethrough and, when reached, displays a single explanatory message in place of the zone's normal screen (naming which registered repos do carry the module) rather than the accent active-fill.
- **Repo registry screen (Story 2.11):** always shows static manifest-creation guidance (manual `.tui-back.yaml`, or the manifest-generator skill) alongside scan/register controls, not just on first launch; reachable only via the `registry` command inside Story 2.14's `:` command bar, and auto-offered from a Dashboard "no repos registered yet" prompt that chains *before* the existing "no EDT yet" state when the registry is empty. Scan-in-progress, per-path outcome (registered/already-registered/failed), and a distinct "nothing found here" state (never conflated with a scan failure) are all required states.
- **Command bar (Story 2.14):** opened by `:` from any zone when nothing else has input focus; reuses the `modal-dialog` + `list-row` visual pattern (same family as the `?` help screen); never opens over another overlay; closes on a successful exact-match run or on `Esc` (discarding typed text), and stays open showing "unknown command" on an unmatched `Enter`.

## Cross-Story Dependencies

- Story 2.2 (branch creation) builds directly on 2.1 (EDT creation) and is gated by 2.3's shared-branch rejection.
- Story 2.3's git branch-scope gate is a shared foundation used by 2.2 (creation-time branch naming), 2.4 (protected-switch), and 2.5 (branch changes).
- Story 2.4 depends on Epic 1's per-resource action lock (Story 1.7) for its switch-blocked-during-update behavior.
- Story 2.5's branch-change flow explicitly reuses Story 2.4's protected-switch mechanic.
- Story 2.6's divergence display applies uniformly to every managed service produced by 2.1/2.4/2.5, member or not.
- Sequencing: **2.7 before 2.9** (2.9's new forms must target the finalized nav contract, not the retired one); **2.8 is independent**. 2.9 also depends on 2.1/2.4/2.5's core use-cases already existing (it wires them into the TUI, adding no new core logic) and on 2.6's list as the surface it extends.
- Story 2.10 extends Epic 1's Story 1.7/AD-9 mechanism 1 (single-TUI enforcement) without reopening Epic 1; it touches only the TUI's startup sequence, with no impact on any zone, port, or use-case.
- Story 2.11 is a TUI front-end over Story 1.5's already-shipped `scan`/`register` CLI use-cases — no new core logic. Its "reachable via `:`" criterion depends on Story 2.14's actual trigger mechanism (the `registry` command in the `:` bar) to be truly satisfied.
- Story 2.12 is purely additive to the keybinding contract from Stories 1.13/2.7 — it never touches list-navigation or `Tab`'s existing role inside forms/resize-mode. Its original focus-mode design was renegotiated after a review-caught bug (focus stuck on the tab bar across overlay open/close); the shipped mechanism is a direct, stateless `Left`/`Right` switch instead.
- Story 2.13 depends on Story 2.11 (registry changes can newly show/hide a tab) and Story 2.12 (arrow-navigation must skip omitted tabs and land on disabled ones); it amends Story 1.9/1.11's original always-present tab assumption (text correction, not a reopening) and its version-resolution mechanism (`shared-types-source`) is specified further under Epic 4.
- Story 2.14 supersedes Story 2.11's original (incorrect) implementation, which bound `:` directly to the registry screen; 2.14 builds the actual generic command mechanism the keybinding contract has promised since Story 1.13, and explicitly guarantees it never conflicts with Story 2.12's `Left`/`Right` zone switching (2.14 owns `Tab` while its bar is open; 2.12 never uses `Tab`).
- This epic's git-safety gate (AD-8) and per-EDT storage (AD-7) are reused as-is by Epic 3's group update. Epic 2 must fully merge into `devlopment` before Epic 3 starts.
