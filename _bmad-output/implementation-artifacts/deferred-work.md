## Deferred from: dev of story-1-2-xdg-state-layout-resolution (2026-08-12)

- **Story 1.1's dependency-cruiser/TypeScript 7 gap (item 1 below) is not what actually breaks `depcheck` — a separate, more serious resolution gap is.** Investigation for story 1.2 Task 2 reproduced both a same-folder file containing `interface`/typed-function-signature syntax and a real `src/core → src/adapters` boundary violation using this project's mandatory `tsconfig.json` `"module"/"moduleResolution": "NodeNext"` import style (`import { x } from './foo.js'` resolving to `./foo.ts`, required because the project ships no build step and runs `.ts` directly via `tsx`/Node ESM). Findings:
  - `interface` declarations and simple type annotations parse fine through depcruise's non-TypeScript-API fallback path (acorn-based) even with `typescript@7.0.2` installed and the native TS extractor's `>=2.0.0 <7.0.0` gate active (`node_modules/dependency-cruiser/src/meta.cjs`) — no crash, no silently-dropped file, matching the "acorn tolerates `interface`" hypothesis from Story 1.1's review.
  - `npm view dependency-cruiser versions` confirms `18.2.0` (already pinned) is the latest published release as of 2026-08-12 — no newer version lifts the `typescript@7` gate.
  - However, **any relative import written in this project's required `./foo.js` (resolving to `./foo.ts`) NodeNext style is recorded by depcruise as an edge but flagged `couldNotResolve: true`** — confirmed via `--output-type json` on a deliberately-forbidden `src/core` → `src/adapters` import. Because the `no-core-to-adapters` rule matches on the *resolved* target module, an edge that fails to resolve can never trigger the rule: `npm run depcheck` reported "✔ no dependency violations found" against a real, intentional boundary violation.
  - Setting `options.tsConfig` in `.dependency-cruiser.cjs` does not fix the resolution: it only adds an explicit `missing-typescript-transpiler` warning ("Install typescript to get better results ... Support for typescript@>=7 will follow when its API is published and stable") — the same edge still fails to resolve.
  - There is no supported per-project escape hatch in this dependency-cruiser version: `options.enhancedResolveOptions.extensionAlias` (the setting that would normally teach webpack's `enhanced-resolve` to map `.js` imports back to `.ts` files) is rejected outright by the config schema validator (`must NOT have additional properties`).
  - **Net effect:** `depcheck`'s AD-1 boundary rule (`no-core-to-adapters`) currently cannot catch a violation expressed as a relative NodeNext-style import (the only import style this codebase's `tsconfig.json` allows) — regardless of whether the file's syntax uses `interface`/`type`/generics or none at all. It has been silently non-functional for that import shape since the rule was introduced in Story 1.1; Story 1.1 never exercised it because no cross-file relative import existed yet. Story 1.2's new `xdg/` module does not import across the `core`/`adapters` boundary, so this gap is not exercised by this story's own deliverable — but it will be live risk starting with whichever story first adds a real cross-folder import (Story 1.4 `ManifestPort`/`persistence`, or earlier). **Track and re-verify before merging any story that adds the first real `core/` ↔ `adapters/` relative import** — do not trust a clean `depcheck` run alone once that happens; manually diff the module boundary for that story's file list.
  - No workaround was applied in this story — flagging it as a known, currently-unfixable-in-config gap is the documented "pragmatic path" chosen (per Task 2's guidance), since no dependency-cruiser config option or newer release resolves it as of this date.
