- (decision) [ADOPTED] Paradigm: hexagonal (ports & adapters). Core = EDT lifecycle, script orchestration, log aggregation, route-explorer browse/fire/save mechanics — company/stack-agnostic. Adapters = NestJS/shared-types/gateway-specific modules (driven side) + TUI and CLI (driving side, same use cases). Source: PRD §0, technical research 'Architectural Patterns and Design'.
- (decision) [ADOPTED] Stack: TypeScript (Node.js) + Ink for the TUI layer; better-sqlite3 for local storage; dockerode for Docker log streaming/container control; openapi-typescript against the gateway's OpenAPI spec; jose for dev-mode JWT auth. Settled by technical-typescript-vs-go research report, carried forward as non-negotiable by PRD §0.
- (decision) [ADOPTED] Every Must-scope action is a standalone, parameterized, idempotent script (Command pattern), invocable identically from TUI or shell (FR-1). Subprocess boundary (not in-process function call) is what delivers script/CLI parity.
- (constraint) [ADOPTED] Manifest is a per-repo, in-repo-versioned declaration of service identity + active modules (FR-2); it is the plugin-registration mechanism. Exact schema/format/location is this architecture run's job (PRD Open Question 1).
- (constraint) [ADOPTED] Local state layout follows XDG Base Directory conventions (XDG_CONFIG_HOME/XDG_DATA_HOME/XDG_STATE_HOME/XDG_CACHE_HOME) — PRD Cross-Cutting NFRs, research 'Deployment and Operations Practices'.
- (constraint) [ADOPTED] Storage pattern: database-per-tenant via SQLite, one file per EDT (EDT-scoped state trivially isolated/portable) + one separate, narrowly-scoped global store for cross-EDT data (FR-23 saved-request library) so a bug there can't touch EDT-specific state. Exact file naming/location/schema-migration mechanism deferred to this run.
- (constraint) [ADOPTED] Single-instance enforcement required — a second running instance on the same machine must be detected and blocked (concurrent SQLite/git writers are unsafe).
- (constraint) [ADOPTED] Git safety (non-negotiable, PRD Constraints and Guardrails): only local repo copies ever touched; write access limited to the developer's own feature/fix branches; development/preprod/prod are read-only to the tool; no commit or push without explicit developer approval at the moment it happens; an EDT must never register a shared/protected branch as its own (FR-7). Research recommends enforcing branch-scope checks at the git-adapter layer before any write reaches the actual git invocation, not trusting call sites.
- (constraint) [ADOPTED] Performance NFR: UI interaction response under ~150ms; a log line visible within ~1s of container emission. Log-stream re-renders must be debounced/batched from day one (not a later optimization), given Ink's ~30 FPS render ceiling.
- (decision) [ADOPTED] Risk mitigation: Ink's ~30 FPS/>~50MB ceiling is a monitored risk with a pre-identified same-ecosystem fallback (OpenTUI, React/TS API + Zig core via Bun) if SM-8 shows it's hit in practice — no action now, no code branching for it.
- (constraint) [ADOPTED] UX spine (Atelier, ux-tui-back-2026-08-10) fixes: 3 fixed chrome rows (top bar / zone-tab bar / footer) + resizable content split; 6 zones (Dashboard, EDTs, Update, Logs, Routes, shared-types); list/detail split as the dominant content pattern; modal-dialog for confirmations and guided-resolution menus (FR-11) and the keybinding-help screen. This shapes the TUI driving-adapter's screen/navigation structure.
- (decision) Script contract = single umbrella CLI binary with registered subcommands (e.g. `tui-back run update-repo --edt=...`), not N independent script files/binaries. Binds: FR-1. Prevents: N separate build/package units and duplicated arg-parsing/output-envelope boilerplate per script; keeps one build target. TUI and shell both invoke the same subcommand, which itself is a thin CLI-adapter wrapper around a single hexagonal core use-case/port call — the subcommand is the unit of 'a script', not a standalone file. User confirmed directly (no counter-proposal).
- (direction) Moving to cluster 2: manifest schema (format, location, module-activation shape) and the separate repo-registry question (where the tool learns managed-repo filesystem paths, since the manifest itself lives inside each repo and can't self-announce its path).
- (decision) Manifest = single root file `.tui-back.yaml` per managed repo, YAML, validated at load via zod schema. Fields: service (identity), container (docker-compose/container target name), migrationCommand, sharedBranch (optional override, default 'development' — FR-8), modules (map of module-id -> per-module config, e.g. route-explorer: {scanner, auth}). No explicit schemaVersion field in v1 (single author, no migration need yet). Binds: FR-2, FR-19, FR-20. Prevents: activating a module or adding a repo from requiring core code changes.
- (decision) Repo registry (which local filesystem paths the tool scans) is explicit and NOT assumed to live under one fixed root folder — deliberately kept flexible because the tool may be handed to teammates later (PRD secondary persona) whose local layout is unknown. Populated primarily via an explicit 'register this path' action; a separate wide-scan command (walk a given root, or the whole home dir, looking for repos carrying a .tui-back.yaml) is a discovery convenience that surfaces candidates for the developer to confirm — it proposes, it never auto-registers. Binds: FR-2, repo discovery. Prevents: hardcoding a single-machine directory assumption that breaks on a teammate's differently-laid-out machine. User-directed (rejected the fixed-root-folder default).
- (decision) Module registration = static, compiled-in registry (map of module id -> implementation) inside the tool; manifest only selects a key among modules the tool already knows. No dynamic/external code loading in v1. Binds: FR-2, FR-19, FR-20. Prevents: an arbitrary-code-execution surface on a tool with real (if scoped) git write authority, and unneeded plugin-loader complexity the PRD never asked for. User confirmed directly.
- (decision) Hexagonal boundary, concrete: core/ (edt, scripts, logs, routes use-cases + ports/ interfaces) has zero import of Ink/React/dockerode/child_process/better-sqlite3/fs; adapters/driven/* (git, docker, process, persistence, manifest, registry, modules/*) implement core's ports; adapters/driving/* (tui, cli) call core use-cases only, never a driven adapter directly. Dependency direction: driving -> core <- driven, core depends on neither. Binds: all. Prevents: a TUI-only side effect (violates FR-1), and adapters importing each other directly instead of going through core ports. Git-adapter specifically enforces branch-scope safety checks before any git write reaches the git invocation itself (research recommendation, PRD Safety — Git Access).
- (decision) TUI cross-zone state (active EDT, per-service status, log buffers, in-flight script/run status) lives in one application-level store, not scattered per-zone local state; zone-local UI state (list cursor, scroll position) stays component-local useState. Store implementation: Zustand (over bare useReducer+Context) — chosen for ergonomics and for testing core-driven state transitions outside of Ink's render tree, which matters given the research-flagged gap in Ink-specific testing tooling (no ink-testing-library equivalent). Binds: FR-16/17/18 (log view), FR-6/9 (EDT/branch status), FR-10/11/12 (run status). Prevents: per-zone state fragmentation losing track of 'which of N concurrent things changed' (research finding). User confirmed the central-store call, deferred the library pick — resolved here since both options satisfy the invariant equally and Zustand's testability edge is decisive given the Ink-testing gap.
- (decision) EDT SQLite files named by opaque generated id (ULID), not by topic slug (e.g. XDG_DATA_HOME/tui-back/edts/<ulid>.db); topic stored as a field inside the file. FR-3 topic-uniqueness check requires reading the topic field across existing EDT files (cheap at this EDT-count scale) rather than a filesystem-existence check. Binds: FR-3, FR-5, EDT storage. Prevents: a future EDT-rename feature forcing a file-rename/migration. User explicitly chose to hedge against a future rename over v1 filename readability.

- (decision) Logs are never persisted by the tool itself: each docker logs -f stream feeds a bounded in-memory ring buffer per service (sized to cover FR-22's fire-correlation window plus session scroll-back), discarded on tool restart. Docker itself remains the source of historical log truth (docker logs). Binds: FR-16, FR-17, FR-22. Prevents: unbounded local log storage growth and a second, tool-owned source of log truth to keep consistent with Docker's. Exact FR-22 window duration left to bmad-ux (mechanism only, decided here).
- (decision) Testing strategy: core/ (use-cases+ports) unit-tested with Vitest against fake port implementations (no real git/docker/sqlite); adapters/driven/* integration-tested against the real system where practical (better-sqlite3 on temp file, git on temp repo); the Zustand cross-zone store is tested directly without rendering Ink; tui/ (Ink components) gets smoke-tests via Ink's own render() only, not exhaustive render coverage — accepted trade-off given the research-documented lack of an ink-testing-library equivalent, since core+store already carry the real logic coverage. Binds: all. User confirmed.
- (decision) Script output envelope (FR-1): stdout is human-readable text when the command runs attached to a TTY, and a single final JSON line (`{ok:true,data:{...}}` or `{ok:false,error:{code,message,details}}`) when it doesn't (TUI spawns non-TTY, always gets JSON with no flag needed) — TTY-detection based, not a --json flag. Exit code: 0 success / 1 failure only; fine-grained detail lives in the JSON error.code, not in exit-code taxonomy. Binds: FR-1, all scripts/subcommands. Prevents: TUI and hand-invocation needing separate code paths or a flag the developer has to remember. User confirmed.
- (decision) Storage topology, remaining pieces: global store at XDG_DATA_HOME/tui-back/global.db (saved-request library FR-21, per-EDT hide/favorite flags, global favorites — FR-23); active-EDT pointer + transient UI state (last-used EDT, log-view scroll position) at XDG_STATE_HOME/tui-back/state.json, not in a .db (durable EDT/global data vs transient state kept on separate XDG tiers); repo registry (managed local paths) at XDG_CONFIG_HOME/tui-back/registry.yaml, same format family as the manifest. Binds: FR-6, FR-21, FR-23, repo discovery. User confirmed as proposed (non-contentious block).

- (decision) BLOCKER FIX: process model clarified. TUI and CLI are two separate process-launches of the same single binary, each calling the same core use-cases IN-PROCESS (direct function calls) — the TUI never spawns a subprocess of itself to perform its own actions. FR-1 parity (TUI vs hand-invocation being identical) is delivered by both driving adapters wrapping the same core use-case code, not by the TUI shelling out to the CLI. AD-2 reworded accordingly; AD-1's diagram was already correct (TUI-->core, CLI-->core, both direct) and stays as-is. Resolves the AD-1/AD-2 contradiction.
- (decision) BLOCKER FIX: AD-9 rescoped. The single-instance lock applies only to the interactive TUI process (only one TUI at a time) — a CLI subcommand invocation is a separate, expected-to-be-concurrent process type and is never blocked by the TUI's own lock (resolves the self-deadlock). Added a second, narrower mechanism: any state-mutating action (from TUI or CLI alike) acquires a short-lived advisory lock scoped to the EDT/repo(s) it actually touches, serializing concurrent writers (two CLI invocations, or a CLI invocation racing the TUI's own in-flight action) instead of corrupting state — this is the real concurrency risk the PRD's 'concurrent writers... unsafe' NFR was pointing at, broadened correctly by the reviewer gate.
- (decision) BLOCKER FIX: active-EDT source of truth clarified — state.json (AD-7) is durable/authoritative; the TUI's Zustand activeEdt field is a hydrated, re-synced cache (loaded at TUI startup, re-read via fs.watch/poll so a CLI-driven change while the TUI is open is picked up, never silently stale). Log buffers clarified — the ring buffer is owned by core/logs (not the docker adapter, which only streams raw lines in); the Zustand store's log-buffer field holds the current rendered/debounced window sourced from core/logs, not an independent second buffer.
