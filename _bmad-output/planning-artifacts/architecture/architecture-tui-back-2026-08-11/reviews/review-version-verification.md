# Review — Version/Currency Verification Audit

**Target:** `ARCHITECTURE-SPINE.md` (tui-back, 2026-08-11)
**Lens:** every committed decision that depends on a "current" external fact (a library version, a runtime default, a tool's capability/ceiling, the existence of an ecosystem tool) must trace to either the memlog's verified research or an independently reproducible web check — not to training-data assertion.
**Method:** re-fetched `registry.npmjs.org/<pkg>/latest` for all 14 stack entries; web-searched Node.js 24 LTS status, TypeScript 7 GA status, `ink-testing-library` currency/compatibility, and OpenTUI's description, since those are the non-stack-table "current fact" claims embedded in the ADs.

## Verdict

Mostly solid — 13 of 14 pinned stack versions check out exactly against the live npm registry, and the two headline "fast-moving package" calls (Node 24 LTS, TypeScript 7.0 GA/Go-native) hold up — but the verification pass has a real gap: one stack version (`yaml`) is stale/wrong despite being claimed as web-verified, and one AD (AD-13) asserts a "current" ecosystem fact — no `ink-testing-library` equivalent exists — that is factually false and contradicted by a two-minute check.

## Findings

### 1. [High] `yaml` 2.8.4 is claimed web-verified but is not the current version — the actual latest (2.9.0) predates the claimed verification date by months
- **Spine:** Stack table, `yaml (eemeli) | 2.8.4`.
- **Memlog:** `.memlog.md` line 33, the `(version)` entry, lists `yaml (eemeli) 2.8.4 — npm` alongside the other packages as "Web-verified current versions (2026-08-11)".
- **Check:** `registry.npmjs.org/yaml/latest` currently resolves to **2.9.0**, published (per npm/web search) roughly 3 months before the claimed 2026-08-11 verification date — i.e. it was already the latest release at the time the memlog claims it checked and found 2.8.4.
- **Why it matters:** this is not a "package updated after we checked" situation (which would be forgivable) — 2.9.0 predates the check. It reads as either a copy-paste/stale-cache value never actually round-tripped through a live registry fetch, or a check performed against a cached/wrong source. Notably, `yaml` doesn't appear anywhere in the prior technical-research doc (`technical-typescript-vs-go-local-tui-admin-tool-research-2026-08-07.md` has zero mentions of "yaml"), so this number was introduced fresh in this run, not carried from an earlier source — making the miss harder to explain as inherited staleness.
- **Impact on spine:** low blast radius (`yaml` is used only for manifest/registry parsing, not a load-bearing architectural choice), but it undermines confidence in the "Web-verified" label attached to the rest of the version row, since this is direct proof the verification pass wasn't uniformly reliable.

### 2. [High] AD-13 asserts "the ecosystem's current lack of an `ink-testing-library` equivalent" — the library exists; it's the wrong claim
- **Spine:** AD-13 — *"`adapters/driving/tui` gets smoke-tests via Ink's own `render()` only, not exhaustive render coverage — an accepted trade-off given the ecosystem's current lack of an `ink-testing-library` equivalent..."*
- **Memlog:** the corresponding decision entry (line 29) repeats the same framing — "the research-documented lack of an ink-testing-library equivalent" — and the original 2026-08-07 research doc is the apparent source of this claim, never re-checked during this run's web-verification pass (that pass covered only the 14 package *version numbers*, not this capability claim).
- **Check:** `ink-testing-library` (by the same author as Ink, vadimdemedes) exists on npm and is a real, functioning render/`lastFrame()` testing utility — precisely the kind of library AD-13 says doesn't exist. What's actually true and *should* have been the finding: its latest release is **4.0.0, published May 2024**, built/tested against **Ink v5 and React 18.3.1** — over two years stale relative to the architecture's chosen Ink 7.1.1 / React 19.2.8, with no evidence of Ink 6/7 or React 19 compatibility.
- **Why it matters:** this is exactly the failure mode the review is looking for — a "current capability" assertion about a named tool that was never independently checked, stated as flat fact, and wrong on inspection. The correct, defensible version of AD-13's rationale is "`ink-testing-library` exists but is unmaintained/stale against Ink 7 and React 19, so it's not a safe dependency to add" — a materially different (and more defensible) claim than "no such library exists." The architectural conclusion (smoke-test only, don't invest in exhaustive Ink render coverage) likely survives either way, but the stated justification is currently false and should be corrected before this spine is treated as verified.

### 3. [Medium] AD-12's Ink "~30 FPS / >50MB" ceiling numbers trace only to secondary blog sources, and were never re-touched by this run's verification pass despite Ink's version having moved since they were sourced
- **Spine:** AD-12 — *"Ink's ~30 FPS render ceiling"*; Deferred section — *"OpenTUI migration — only evaluated if Ink's FPS/memory ceiling is actually observed as a problem in practice."*
- **Source trail:** these numbers come from the 2026-08-07 research doc (`...research-2026-08-07.md` lines 180, 437), which cites three sources — youngju.dev ("TUI Renaissance 2026"), Better Stack, and Stork.AI ("The TUI library that's killing Ink") — all third-party commentary/marketing pieces, not Ink's own docs, changelog, or issue tracker. The memlog explicitly flags that Ink itself moved from the "Ink 6" the research doc cited to Ink 7.1.1 during this run ("fast-moving package, re-verified today," memlog line 33) — but that re-verification only touched the version *number*, not whether the FPS/memory characteristics the whole AD-12/OpenTUI-fallback argument rests on still apply to the now-current Ink 7.
- **Why it matters:** the spine is treating a specific numeric ceiling (~30 FPS, >50MB) as a stable enough fact to hang a monitored-risk-with-fallback architecture decision on, but that number's provenance is secondhand blog commentary about a package that has since shipped at least one major version. Not necessarily wrong — but it's an unverified-against-primary-source "current capability" claim living right next to package-version claims that *were* rigorously re-checked, creating an inconsistent verification bar within the same AD.
- **Suggested fix:** either re-confirm against Ink's own repo/issues that the ~30 FPS/>50MB characterization still holds for v7, or soften the AD's phrasing to flag the figures as secondhand/unconfirmed for the current major version.

### 4. [Low] OpenTUI's "same-ecosystem" framing (AD-12) quietly drops the original research's Bun-runtime caveat
- **Spine:** AD-12 — *"OpenTUI is the pre-identified, same-ecosystem fallback."*
- **Check:** independently confirmed OpenTUI is real and matches its description (React/TS bindings over a Zig rendering core, distributed via Bun) — this part is accurate and not hallucinated.
- **Nuance dropped:** the source research doc was more careful, calling OpenTUI "newer and Bun-tied, so it's a fallback to validate later, not a default to start on" (research doc line 437). The spine's "same-ecosystem" phrasing (true for the React/TypeScript API surface) elides that adopting OpenTUI means adding a second JS runtime (Bun) alongside the Node 24 runtime the rest of the stack (AD-14's `tsx`/`node` execution model, `better-sqlite3` native bindings, `dockerode`) is built on — a non-trivial migration, not just a library swap. Low severity because it's explicitly Deferred and not an active decision, but worth tightening if AD-12 is ever promoted out of "deferred."

### 5. [Info/Positive] Stack table coverage vs. memlog verification pass — no gaps found
- Every one of the 14 Stack-table entries (TypeScript, Node.js, Ink, React, Zustand, better-sqlite3, dockerode, openapi-typescript, jose, zod, yaml, ulid, vitest, tsx) is listed in the memlog's `(version)` verification entry — no stack-table technology was pinned without at least a claimed check.
- Spot-checked 13 of 14 directly against `registry.npmjs.org/<pkg>/latest` today; all 13 matched exactly (TypeScript 7.0.2, Ink 7.1.1 incl. `engines: node>=22` and `peerDependencies: react/@types/react >=19.2.0`, React 19.2.8, better-sqlite3 13.0.3, dockerode 5.0.1, jose 6.2.8, openapi-typescript 7.13.0, zod 4.4.3, zustand 5.0.14, vitest 4.1.10, ulid 3.0.2, tsx 4.23.12). Only `yaml` failed the check (Finding 1).
- Independently confirmed Node.js 24 is genuinely Active LTS as of the stated date (transitions to Maintenance LTS 2026-10-20 per current schedule) and that TypeScript 7.0 GA'd 2026-07-08 as a Go-native rewrite — both plausible, both correctly characterized in the spine/memlog, not hallucinated.
- No named technology inside an AD or the Consistency Conventions table falls outside the Stack table's coverage (git, Docker, SQLite-the-format, and XDG conventions are the only other "technologies" named, and none of them carry a spine-asserted version number or capability ceiling that needed checking — they're treated as environment-given, not pinned).

## Notes / Out of Scope Observations (not findings)
- TypeScript 7.0 GA is barely a month old at the architecture's "current date" (GA 2026-07-08, spine dated 2026-08-11) and, per InfoQ, ships **without a stable programmatic API** (typescript-eslint, Vue, Svelte tooling can't yet target it). This doesn't currently break anything in the spine's stack (execution goes through `tsx`/esbuild, not `tsc`'s programmatic API, and no lint tooling is committed in the spine), but it's a freshness risk worth the team's awareness if type-aware lint tooling is added later — not something the spine asserts incorrectly, just an absent caveat.
