# Reconciliation: brief/addendum vs. UX spine (DESIGN.md + EXPERIENCE.md)

Scope: brief.md + addendum.md (source) checked against DESIGN.md + EXPERIENCE.md (spine), 2026-08-11. Six gaps found. Purely backend/technical items with no UI-facing implication were excluded per instructions (e.g. Postgres-per-service, TCP RPC transport, `kafkajs`/RabbitMQ specifics, Docker network topology).

## Gaps

- **Zombie repo (`micro-bookings`) has no UI/state treatment.** The real environment has a 13th folder — no `.git`, no docker-compose, already dropped from the gateway, explicitly skipped by every existing script (addendum, "Repo inventory," line 9). The spine's own philosophy is to never silently omit a service from any summary (EXPERIENCE.md Voice and Tone table, "A summary that silently omits a service's outcome" — Don't, line 49; Update-zone state table, "Per-service outcome," line 99), yet neither DESIGN.md nor EXPERIENCE.md says anything about how a permanently-defunct repo like `micro-bookings` should appear (or be excluded) in EDT-membership selection, the Update zone's service list, or anywhere else. No corresponding location in either spine file.

- **Shared, long-lived fleet-wide branches (e.g. `development-nestmsg`) aren't handled in the EDTs zone's state patterns.** The real environment mixes a long-lived cross-service refactor branch with ticket-scoped branches (addendum, "Conventions observed," line 28). The brief's Non-Negotiable Constraints require "An EDT must never register a shared branch as 'its own'" (brief.md line 71), but EXPERIENCE.md's EDTs State Patterns table (lines 82–89: Empty / Populated / No upstream-offline / Protected-switch blocked / Interrupted update) has no state for "a candidate member service is currently on a shared/long-lived branch, not a personal one" — nothing describing how that's detected, flagged, or blocked during EDT creation/membership.

- **`shared-types` publish-flow detail doesn't match its real-world source, and adds an unsourced command name.** Addendum describes the existing release script as "bump via `jq`, pull → build → publish → push" (addendum, "Conventions observed," line 30). EXPERIENCE.md's UJ-3 step 2 and the shared-types state table instead describe "the tool runs `shared-types`'s own `npm run v` (bump → build → publish → push)" (EXPERIENCE.md line 206; also "Publish in progress" row, line 128) — the `pull` step is dropped from the sequence, and the specific script name `npm run v` doesn't appear anywhere in brief.md or addendum.md (likely carried from the PRD, but it doesn't reconcile against the source-of-truth script description here).

- **Manifest-driven "active company modules" isn't reflected in the always-fixed six-zone navigation.** The brief's Must-scope technical foundation calls for "a per-repo manifest format that also declares which company-specific modules are active" (brief.md line 80), part of the declared generic-core/swappable-module architecture (brief.md Executive Summary, line 14). EXPERIENCE.md's Information Architecture instead presents all six zones — including the company-specific Routes and shared-types modules — as permanently, always-reachable tabs with no mention of conditional/module-aware visibility (EXPERIENCE.md lines 19–34, "Six permanent zones, always reachable from the top bar"). Whether a zone should hide/disable itself when its module isn't declared active for the current manifest is unaddressed in either spine file.

- **Teammate/second-persona framing is absent from both spine files, even as an open question.** The brief names two additional personas that "shape architecture decisions now": teammates/new hires, sold on a setup that "just works" (brief.md "Who This Serves," lines 16–20; Success Criteria, line 55: "a new developer's local environment reaches 'ready to code'... without hand-holding"), and the deferred-but-real second personal-project persona (Java/Python, no gateway). Neither DESIGN.md nor EXPERIENCE.md mentions either persona anywhere — EXPERIENCE.md's Foundation section only states "Single-user: Max is the sole operator of a single running instance" (line 17), which addresses runtime concurrency, not the future-audience framing. Given brief.md explicitly flags this as shaping architecture "now" rather than being purely deferred, its total absence (not even a `[NOTE FOR UX]` open question) is a gap.

- **Architecture-maturity unevenness across services has no corresponding trust/caveat treatment.** Addendum notes the fleet itself is "mid-evolution, not a stable target" — `micro-users` mid-migration to clean architecture, `micro-registrations`'s README flagging missing tests and data-integrity constraints (addendum, "Architecture maturity," lines 32–34). Neither spine file has any state, copy pattern, or Voice-and-Tone guidance acknowledging that some services are less reliable/battle-tested than others (e.g. a maturity indicator, softened confidence language for a known-shaky service's update outcome, etc.) — not present in DESIGN.md or EXPERIENCE.md.
