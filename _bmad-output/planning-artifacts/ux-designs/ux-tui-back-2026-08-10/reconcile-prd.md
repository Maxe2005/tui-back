# PRD ↔ UX Spine Reconciliation

**Scope:** PRD (`prd.md`) vs. `DESIGN.md` + `EXPERIENCE.md`. Checked FR-1–FR-23, UJ-1–UJ-4, Glossary, Cross-Cutting NFRs, Constraints and Guardrails. Items explicitly deferred to `bmad-architecture` (manifest schema, storage topology, script/CLI contract) are out of scope by instruction and excluded below.

**Result: 7 gaps found** — 4 FR consequences with no corresponding state/flow, 1 constraint-framing item dropped in each of two Trust bars, and 1 glossary-term consistency nit. No divergence found between any PRD journey (UJ-1–UJ-4) and its spine Key Flow; no glossary term is used with conflicting meaning across the two spines.

---

## FR gaps — testable consequence with UI implications not reflected in EXPERIENCE.md

- **FR-3 (Create an EDT) — creation-time validation not surfaced as a state.** PRD consequences: "Topic must be unique among existing EDTs; at least one member service is required at creation" (`prd.md` §4.2 FR-3). `EXPERIENCE.md`'s **EDTs** state table (`EXPERIENCE.md` "State Patterns > EDTs") lists Empty / Populated / No upstream-offline / Protected-switch blocked / Interrupted update — no state for a duplicate-topic rejection or a zero-service creation attempt. Not found in spines.

- **FR-4 (Create dev branches for EDT member services) — creation-time config and partial-failure reporting missing.** PRD consequences: one base-branch choice + one naming mode (grouped/individual) applies to the whole creation action, and "a per-service branch-creation failure ... is reported per service and does not abort creation for the others" (`prd.md` §4.2 FR-4). `EXPERIENCE.md`'s Key Flow UJ-1 step 4 ("Atelier ... he has the tool create matching dev branches for both services off `development`, named after the ticket") only shows the happy path — no mention of the base-branch/naming-mode choice as an interaction, and no state for a per-service branch-creation failure anywhere in the EDTs table. Not found in spines.

- **FR-5 (Modify an EDT after creation) — no dedicated flow or states.** PRD consequences: add/remove members without recreating, change a member's branch under the FR-6 protected-switch rule, and "removing an EDT's last remaining member service is allowed — an EDT can exist with zero members" (`prd.md` §4.2 FR-5). `EXPERIENCE.md` only names this capability once, in the IA table ("EDTs | Create, modify, and protected-switch EDTs ... | FR-3–FR-9", `EXPERIENCE.md` "Information Architecture"), with no Key Flow and no state-table entries (e.g. a zero-member EDT display, a mid-edit membership-change confirmation). Not found in spines beyond the one-line IA mention.

- **FR-7 (An EDT never claims a shared branch) — rejection path not surfaced as a state.** PRD consequence: "Attempting to register a protected branch to an EDT fails with a clear explanation, before any git write happens" (`prd.md` §4.2 FR-7). This is also called out as one of the Safety — Git Access bars ("An EDT must never register a shared branch as its own (FR-7)", `prd.md` "Constraints and Guardrails"). No corresponding entry exists in `EXPERIENCE.md`'s EDTs state table or Key Flow UJ-1/UJ-4. Not found in spines.

- **FR-21 (Save, customize, and re-fire a request) — name-collision rejection not surfaced as a state.** PRD consequence: "Save-as-new is rejected on a name collision with an existing saved request; the developer is prompted to choose a different name" (`prd.md` §4.6 FR-21). `EXPERIENCE.md`'s Routes state table (`EXPERIENCE.md` "State Patterns > Routes") covers Scan in progress / Scan failure vs. empty / Fired-response / Auth error / Unlearned affected-service set / Stale saved request / Library hide-favorite — no entry for a save-as-new naming collision, and Key Flow UJ-2 step 3 only depicts the non-colliding overwrite-or-save-as-new choice. Not found in spines.

## Constraints and Guardrails — framing/nuance flattened or dropped

- **Trust — Usability bar not restated.** PRD: "Navigation must never be confusing enough to cause outright rejection of the tool — a non-negotiable bar carried from the brief, not a polish item to defer. Directly informs the still-open UI/UX approach decision" (`prd.md` "Constraints and Guardrails > Trust — Usability"). `EXPERIENCE.md`'s Navigation model (top bar, zone-tab bar, list/detail split — `EXPERIENCE.md` "Information Architecture") specifies the mechanics this bar is meant to satisfy, but nowhere restates the stakes behind it (that confusing navigation is a rejection-causing failure mode, not a polish item) — e.g. the Open Questions list treats undecided zone mnemonics and minimum-width behavior as ordinary `[NOTE FOR UX]` items with no flag that they bear on this non-negotiable bar. Not found in spines as an explicit principle.

- **Trust — Single Source of Truth stated only through its three instances, never as the governing principle.** PRD: "The tool must never force a developer to check another source to get the full picture. This is a blanket bar, not a per-feature one ... and any feature added later is expected to satisfy it too" (`prd.md` "Constraints and Guardrails > Trust — Single Source of Truth"). `EXPERIENCE.md` faithfully implements the three cited instances (FR-9 branch/divergence in the EDTs table, FR-18 inline health in the Logs table, FR-22 response+logs in the Routes table), but the phrase "single source of truth" / the blanket, forward-looking framing itself never appears in either spine file — so a future zone author reading only `EXPERIENCE.md` has no standing principle to apply, only three worked examples. Not found in spines.

## Glossary — term used inconsistently

- **"Assisted resolution" not applied to the migration-failure/publish-failure states it's defined to cover.** Glossary: "Assisted resolution — The tool's detect → (auto-fix known-safe cases, else guided menu) → re-verify loop **for merge conflicts and migration failures**" (`prd.md` §3, emphasis added), and FR-13's note explicitly extends "the same detect → fix → re-verify guarantee as FR-11/FR-12" to `shared-types` publishing (`prd.md` §4.4 FR-13). In `EXPERIENCE.md`'s Update state table, only the merge-conflict case is literally labeled "**Assisted-resolution menu**" (FR-11); the "Migration failure" row (FR-12) and the shared-types "Publish step failure" row (FR-13) describe the identical detect→fix→re-verify mechanic without using the term, so a reader of `EXPERIENCE.md` alone would not necessarily recognize all three as the one named mechanic the glossary defines. `prd.md` §3 Glossary vs. `EXPERIENCE.md` "State Patterns > Update" and "> shared-types".
