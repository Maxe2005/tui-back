# Reconciliation: Technical Research vs UX Spine (DESIGN.md / EXPERIENCE.md)

**Sources compared:**
- Research: `_bmad-output/planning-artifacts/research/technical-typescript-vs-go-local-tui-admin-tool-research-2026-08-07.md`
- Spine: `_bmad-output/planning-artifacts/ux-designs/ux-tui-back-2026-08-10/DESIGN.md`, `EXPERIENCE.md`

**Result: 2 gaps found.** Both are omissions (a research finding with UX implications that isn't carried into the spine as a named risk/state), not factual contradictions — nothing in the spines actively misstates an Ink capability from the research.

---

- **Gap 1 — Ink's ~30 FPS render cap / >50 MB memory ceiling is not named anywhere in the spine, only its mitigation tactic is.**
  Research (`## Technology Stack Analysis > TUI Framework Ecosystem`, `## Risk Assessment and Mitigation`, and Implementation Roadmap item 5) treats Ink's hardcoded ~30 FPS render cap and >50 MB baseline memory footprint as a real, "known, bounded architectural ceiling" that must be "treated as a monitored risk, not a blocker," with OpenTUI identified as a specific, pre-validated escape hatch if the ceiling is hit in real usage — and flags the aggregated multi-service log view (the exact surface `EXPERIENCE.md` scopes to "≤10 `docker logs -f` streams... into one filterable view") as the place most likely to hit it.
  `EXPERIENCE.md`'s `## State Patterns > Logs > Streaming` row does carry the recommended *mitigation* ("Live aggregated stream, debounced/batched re-renders"), and `DESIGN.md`'s `## Elevation & Depth` motion note ("~150ms perceived-response bar," spinner as the only animated element) is consistent with staying under the cap. But neither spine file names the underlying constraint itself, scopes it beyond the Logs zone (e.g. Update's per-service concurrent spinners, `## State Patterns > Update > In progress`, aren't discussed against this ceiling at all), or records the OpenTUI fallback path. Every other unresolved risk of this kind in the spine is explicitly logged under `EXPERIENCE.md`'s `## Open Questions` with a `[NOTE FOR UX]` tag; this one has no equivalent entry, so an implementer reading only the UX spine has no visibility into why the debounce rule exists or what to do if it's insufficient.

- **Gap 2 — No spine state covers quitting the app while a run (group-update, publish, propagation) is mid-flight, despite research specifying the shutdown behavior.**
  Research (`## OS Signal Handling & Process/Docker Integration`) establishes a specific graceful-shutdown contract for `SIGINT`/`SIGTERM`: stop log tailing, close DB handles, but leave running containers alone (git/Docker are never force-killed). This is a real, user-facing question — what happens if Max presses `[q]` (the documented quit key, `DESIGN.md`'s `## Components > footer-hint` example: `[q] quit`) while, say, a group update is mid-run (`EXPERIENCE.md`'s `## State Patterns > Update > In progress`)?
  `EXPERIENCE.md` already has a directly parallel precedent for a *different* interruption case — `## State Patterns > EDTs > Protected-switch blocked` / `Interrupted update` blocks/handles switching *away from* an EDT mid-update and surfaces a resumable "interrupted" state — but there is no equivalent entry for quitting the whole application mid-run (Update, shared-types publish/propagation, or an in-progress Logs restart). Given the research explicitly scoped this shutdown behavior as part of the tool's technical foundation, the spine's silence on the matching UI state (confirm-before-quit? resume-on-relaunch? nothing?) is a gap worth closing before implementation.
