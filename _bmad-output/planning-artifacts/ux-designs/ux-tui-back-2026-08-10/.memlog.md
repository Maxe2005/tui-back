Named instances already in PRD: FR-9 (branch/divergence inline), FR-18 (inline health next to logs), FR-22 (response + logs together) — any new feature is expected to satisfy it too.
- (decision) [from PRD] Perf NFR directly shapes interaction feel: UI response under ~150ms, a log line visible within ~1s of emission; log-stream re-renders must be debounced/batched (not full redraw per line) to stay responsive under up to ~10 concurrent docker-logs streams. Sluggishness is a stated deal-breaker (sends developer back to bash).
- (decision) [from PRD] Monitored risk (Open Question 3): Ink's documented ceiling (~30 FPS render cap, >50 MB baseline memory) is unconfirmed in practice; OpenTUI (same React/TS API, Zig rendering core via Bun) is the pre-identified fallback if the aggregated log view hits it. No action now; revisit only if observed.

- (decision) [from addendum] micro-bookings is a 'zombie' repo: no .git, no docker-compose, already removed from the gateway, but still sits in the working tree as cruft, explicitly skipped by existing scripts — the managed-repo list UI needs a way to exclude/flag repos like this rather than assuming every folder is live.
- (decision) [from addendum] Existing update-services.sh (today's 'update everything' entrypoint) is run by hand roughly every 2-3 days, evidenced by ~11 logged sessions July-Aug 2026 writing timestamped logs to logs_updates/ — a real usage-cadence baseline the group-update UX should feel at least as fast/trustworthy as.
- (decision) [from addendum] update_repo.sh today auto-resets uncommitted changes only when just package.json/lockfile are dirty, otherwise prompts the developer — an existing convention for what counts as 'safe to silently handle' vs. what needs an explicit human decision, worth carrying into the new tool's confirmation-gate design.
- (decision) [from addendum] check_health.sh polls the gateway's /health/all and auto-restarts any failing service via a hardcoded SERVICE_MAP; only the gateway exposes health endpoints today (/health/:name, /health/all) — no per-service health endpoints exist, which constrains what an aggregated health view can actually show.
- (decision) [from addendum] audit-messages-pattern.js found 544 declared RPC message patterns, 364 active, 170 orphaned (31%) — a concrete, ready-made data point for why cross-service visibility matters, and a candidate future insight/health surface for the tool's UI.
- (decision) [from addendum] No manifest or service registry exists anywhere today — every script hand-encodes the service list and container-naming convention (<short-name>-back), duplicated and brittle. Directly validates the per-repo manifest as the tool's single source of truth for what services exist and how to address them.
- (decision) [from addendum] Real branch-naming conventions observed: a shared long-lived fleet-wide branch (e.g. development-nestmsg) alongside ticket-scoped feature branches (feat/IWR-####/kebab-case-description, Jira-style) — the EDT/branch UI should recognize and display both patterns naturally.
- (decision) [from addendum] shared-types already has its own one-command 'release everything' script (bump via jq, then pull -> build -> publish -> push) — cited in the addendum as a useful reference point for what a good propagation UX could look/feel like.
- (decision) [from addendum] Architecture maturity is uneven across the fleet (e.g. micro-users mid-migration to clean architecture, micro-registrations's README flags missing tests/data-integrity constraints) — the tool will operate against services that are themselves mid-evolution, not a stable target, so UI states should tolerate inconsistency across services rather than assume uniformity.
- (decision) [from addendum] Tech stack detail relevant to log/health UX: 100% Node/NestJS (one service still on older CLI version), TypeORM+Postgres per service each in its own container, gateway-to-service RPC over TCP (not a broker), RabbitMQ centrally hosted for inter-service events, no root-level docker-compose (every repo has its own, joined on a shared external Docker network). kafkajs is present in ~6 services with no Kafka broker anywhere, flagged as likely-vestigial tech debt worth surfacing if the tool ever shows dependency health.
- (decision) [from research] Ink (TypeScript/React) has production precedent at scale in exactly this tool category — it powers Claude Code, GitHub Copilot CLI, Gemini CLI, and Gatsby CLI. Recommended stack is Ink 6 + React 19, giving near-zero ramp-up from the author's existing NestJS/React-adjacent fluency for component/hook-based UI design.
- (decision) [from research] Recommended interaction/state-architecture pattern for the UI: a reducer-based state store (React useReducer) inside Ink's JSX tree, reproducing the same unidirectional-flow discipline as the Elm Architecture (MVU) used by Go TUI frameworks — chosen specifically to keep 'which of N concurrent things changed' tractable as the tool juggles concurrent log streams, script-run status, and EDT-switch state across more than one screen.
- (decision) [from research] CLI design guidance (clig.dev) cited as the basis for the 'every action is a script' architecture: each script should expose a uniform, disciplined invocation contract (args in; structured stdout such as JSON lines; exit codes out) — relevant to how the TUI surfaces consistent action progress/results/errors to the developer across all script-backed actions.
