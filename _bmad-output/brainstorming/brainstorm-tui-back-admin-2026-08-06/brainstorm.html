Brainstorming keepsake

A dev builds a cockpit for their own backend.

One evening, four techniques, one recurring question: how do you stop babysitting a fleet of NestJS microservices by hand — the repos, the logs, the branches, the migrations, the constant workspace-switching — without losing trust in the tool that's supposed to help. This page retraces the session, in order, exactly as it unfolded.

🎭 Act I — Role Playing

Four voices, one tool

Before any architecture, the session put four people in front of the same imagined tool and let each of them react from their own vantage point.

[daily-user] — the everyday dev

The one who lives in it, every day

Wants the tool to disappear into muscle memory: fast, contextual, always where they left off.

  • The tool should know the current workspace at startup — context persists between sessions.
  • Batch-update every repo in a workspace to the latest shared "dev" version, migrations run automatically.
  • Then choose to selectively propagate that update to one or more other active workspaces.
  • Show errors (migration, update) right inside the tool — never force a step outside it.
  • Microservices in the workspace launch automatically when it's opened.
  • Service status at two levels: per-repo detail, and a global dashboard.
  • Switching workspace instantly resumes the in-progress coding session — branch and context intact.
  • Search and fire a gateway route directly from the tool.
  • Remember routes already used in this workspace — contextual history, per workspace.
  • Keep the body/params used per request, reusable in one click.
  • After sending a request, see the logs immediately — single view or global dashboard.
  • Fast loop: error spotted in logs → fix shared-types → propagate to every micro in the workspace, one action.
[new-hire] — onboarding day one

The one who's never seen this stack

Wants a tool that never leaves them stranded, and teaches the stack while it sets it up.

  • Guided, step-by-step install that never fails silently.
  • Built-in, accessible help — for the tool AND for the whole stack, not just its own UI.
  • If a micro repo isn't found: offer to either point to its existing location, or install it automatically.
  • On install failure: maximum guidance for known errors (a solutions library) — and for unknown ones, surface every useful log so they can self-debug, or hand it to a senior.
  • By the end of setup, the environment is 100% ready to code — or at least to explore the stack immediately.
[tech-lead] — owns the guardrails

The one who thinks in years, not sessions

Wants the tool to keep working as the stack evolves — and to never overstep what it's allowed to touch.

  • Design it to evolve easily: the stack keeps changing, so the architecture must be modular and adaptable, never frozen.
  • Security boundary: the tool administers only the dev's local repo copies — never a remote environment.
  • Security boundary: no commit or push without the dev's explicit consent — never a silent git action.
  • Correction mid-session: the tool must never commit or push to development, preprod, or prod — only to feature/fix/refactor branches of the current work.
  • It may only read shared branches (development/preprod/prod), to sync or update dev branches from them.
  • A workspace must never register a shared branch as "its own" — only dev branches proper to each concerned micro.
[colleague] — working in parallel

The one sitting three desks over

Wants to know: if we both use this at once, what breaks?

  • Each dev works on their own machine, with their own local instance of the tool and their own Dockers.
  • The only possible collision between colleagues is at the git level — never Docker, ports, or local resources.

🧩 Act II — Morphological Analysis

Five axes, options laid side by side

The four voices converged into five independent design axes. Each was cranked for options — some settled into decisions on the spot, others stayed open for later.

Axis Options generated
Axis 1Language / tech Go + Bubbletea Python + Textual Node.js / TypeScript — same stack as the backend, understood by every dev A minimal TUI (gum / fzf / dialog) that just orchestrates independent CLI scripts, each runnable standalone ↳ seeds the synthesis
Axis 2Workspace config storage Stays local — no network/cloud sync Decided Multiple small files rather than one big file Decided Single SQLite store — no text/SQLite mix, since this data was never meant to be hand-edited Decided
Axis 3UI/UX organization Multi-pane layout, k9s / lazygit style: a workspace-and-repos sidebar + a contextual central panel, plus a universal command palette (Ctrl+K) with fuzzy search to jump anywhere — including finding a gateway route
Axis 4External scriptability Every action = a script with detailed, precise parameters — called and auto-filled by the TUI, but also directly runnable by hand for combinations the UI never anticipated ↳ becomes the session's synthesis Use cases named on the spot: a colleague repurposing a script for a different need; a future automation or CI chaining several together
Axis 5Long-term evolvability Everything configurable and modular, to absorb a new micro or a process change (e.g. branch naming convention, shared-types evolution) A per-repo manifest (repo.yaml) describing its own conventions — migration, branch naming, restart, healthcheck — so the TUI stays generic: adding a micro just means adding its manifest

🏰 Act III — Disney Method

Three rooms, one door at a time

Dream without limits, then get concrete, then tear it apart. Each room only sees what the previous one left behind.

The Dreamer

No constraints. What would the tool do if it could do anything?

  • The tool handles everything outside pure code: the full local git workflow, local Docker management, updates, migrations — and smooths the entire stack install for a new dev.
  • It's connected to an AI assistant (Claude-like) that anticipates and fixes errors directly, for a calmer dev experience.
  • The AI formalizes and automates the git workflow on the dev's behalf.
  • The AI serves up views and actions already "clean" and adapted to the moment's context — the dev never has to build them.

The Realist

Okay — what would it actually take to build that?

  • The "action = standalone script" idea from Axis 4 is exactly what makes AI integration realistic: an AI can execute a script far more reliably than it can operate an interactive TUI.
  • Shared-types propagation becomes a single triggerable action (shortcut or command): ask for the target version, apply it to every micro in the workspace.
package.json→npm i→restart docker→health_check
  • On failure, show that micro's Docker logs directly — no manual digging.

The Critic

Where does this fall apart?

  • Major critique: for automated actions to succeed, the tool alone has to resolve a huge number of minor problems — one unhandled edge case fails the whole action. New failure modes keep appearing; robustness is never "finished".
  • AI-executor risk: a poorly-bounded AI could saturate CPU by restarting micros in an infinite loop, or destroy work in progress if misconfigured. Strict guardrails — rate-limiting, confirmation, limited scope — are required before any AI auto-execution.

🎯 Act IV — Job to Be Done

What does the dev actually hire this tool to do?

Strip away the feature list and three jobs remain — plain, unglamorous, and exactly what's eating the day.

01

Search & aggregate logs

Find and assemble the log screens — search and aggregation across multiple sources at once, instead of tab-hopping between terminals.

"Done well" = see one micro's logs in isolation, in seconds, AND get a dashboard aggregating several micro logs on a single interface.
02

Own the tedious repo lifecycle

Handle the "annoying" parts of repo life — updates, migrations, conflicts — on the dev's behalf, instead of the dev doing it by hand every time.

03

Switch workspaces, frictionless

Move between two work sessions (workspaces) without friction — and without the dread of what might get lost in the process.

Deep motivation Not survival — comfort and efficiency. All three jobs are about reclaiming time from actions that are repetitive and simply not fun.
Today's "competitor" A polished internal tool — really just a handful of personal, hacked-together scripts, and everything else done by hand.

⚠ Non-negotiables

Every idea in this session answers to two short lists. Break one of these, and the tool isn't the solution anymore — it's the new problem.

Trust deal-breakers

DB-1

Losing uncommitted changes on a workspace switch destroys trust instantly — auto stash/save per workspace is non-negotiable.

DB-2

Slowness sends the dev straight back to their bash scripts.

DB-3

Confusing or hard navigation gets the tool abandoned.

DB-4

Showing an error isn't enough if fixing it means re-running logs by hand — an integrated resolution loop is required, not just a mirror of the logs.

DB-5

An incomplete view that forces a check elsewhere breaks the tool's promise of being the single source of truth.

Git security boundaries

SEC-1

The tool administers only the dev's local repo copies — never a remote environment.

SEC-2

No commit or push without the dev's explicit consent — never a silent git action.

SEC-3

Push, at most, to feature/dev branches — never to development, preprod, or prod. Common branches may only be read, to sync dev branches from them.

✨ Finale — The Synthesis

One idea, quietly doing four jobs at once

Traced back through all four techniques, one architectural choice keeps resurfacing — and one workflow becomes the first proof it actually works.

Central architectural idea

Every action is a standalone script.

🤖

AI-executable

An AI can run a well-scoped script far more reliably than it can drive an interactive TUI — this is what the Disney "Realist" room hinges on.

🔌

Externally scriptable

Axis 4's answer, directly: usable by hand, repurposed by a colleague, or chained by a future CI.

🧭

Guided onboarding

The new hire's step-by-step install is just this same idea, run once, in order, with nothing hidden.

🔒

A vector for guardrails

Because each action is a discrete, auditable unit, the security boundaries and safety limits have somewhere concrete to attach.

First concrete implementation of Deal-breaker #4

The shared-types propagation flow

edit package.json→ npm i→ restart micro's docker→ health_check
⤷ on failure show that micro's docker logs, right here

Born in the Disney "Realist" room — this is the pattern to reproduce for every future automated action.

Directions retained for future convergence
  • ✔"Action = standalone script" as the architectural cornerstone.
  • ✔Workspace storage: local, multi-file, single SQLite store.
  • ✔Per-repo manifest as the mechanism for long-term evolvability.
  • ✔The 5 trust deal-breakers and 3 git security boundaries stand as non-negotiable acceptance criteria.
